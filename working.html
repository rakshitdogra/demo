How this prototype works

Everything here runs client-side, in one HTML file, against an in-memory data set. Nothing is sent to a server, and reloading the page restores the seeded demo data. This page explains what's real logic and what's simulated.

Overview

The prototype is a single shared data store — a list of "challenges" — viewed through five different role tabs. Actions taken in one role (validating, accepting, funding, deploying) mutate that shared store, so the effect is visible immediately from every other role.

Try this: validate a challenge as Government, then switch to University — it will now appear in that institution's ranked matches.

Roles

Each tab is a different lens on the same data, with its own set of actions.

Citizen

Submits new reports and sees them classified live. Can track any report through its full status history.

Government

Works the review queue — moves reports from Submitted → Under Review → Validated. Sees domain totals computed from live data.

University

Switches between four institutions, sees challenges ranked by computed match score, and accepts them to spin up a demo team.

Industry

Sees only challenges that are matched to a university and in development, offers support, and can mark a project deployed.

Admin

A flat table of every challenge, at whatever stage it currently sits, with its assigned university and industry partner.

Status lifecycle

A challenge moves through six stages. Only the actions listed can advance it — there's no way to skip a stage from the UI.

AI classifier

The "AI" in this prototype is a transparent keyword matcher, not a model call — it's deterministic so the demo behaves the same way every time.

How it decides a domain

Every submission's title and description is checked against six keyword lists (water, health, agriculture, education, infrastructure, environment). Whichever domain has the most keyword hits wins; infrastructure is the default when nothing matches.

How it decides severity

Two or more keyword hits → High. Exactly one → Medium. None → Low. It's a proxy for how clearly a report fits a known problem category, not a real urgency assessment.

Matching algorithm

Each university has a short list of capability tags (its domains of strength). A challenge's match score against a university is built from that overlap, plus a small fixed "jitter" so scores don't feel identical across similar challenges.

ComponentContribution
Base score40 points, every challenge starts here
Domain match+40 if the challenge's domain is one of the university's tags, otherwise +8
Variation+0–14, derived deterministically from the challenge and university IDs

Because the variation is derived from IDs rather than Math.random(), the same challenge always scores the same way against the same university — refreshing the page won't reshuffle the rankings.

Data model

A challenge object looks roughly like this:

id, title, desc, district, affected,
status, domain, severity, keywords,
university, industry, team,
impactBefore, impactAfter, submittedAt

Eight demo challenges are seeded on load, spanning every stage of the lifecycle so all five role views have something to show immediately. Four demo universities and three demo industry partners are fixed reference data, not editable from the UI.

Prototype limits

What this build intentionally leaves out, since it's meant to demonstrate the workflow rather than be production-ready:

No persistence — data lives in memory and resets on reload, or on demand via "Reset demo data."

No authentication — anyone opening the file can act as any role.

No duplicate detection, multilingual intake, or real district map — these are described in the earlier concept report but not built here.

Impact numbers for newly deployed projects are generated from a formula, not measured field data.
